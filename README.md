# لعبة المسابقات الجماعية

موقع ثابت (HTML/CSS/JS بدون فريمورك أو build tools) للعبة مسابقات جماعية بنظام هوست،
يتزامن فوريًا بين جوال الهوست وشاشة العرض عبر Firebase Realtime Database.

## هيكل الملفات

- `index.html` + `js/index-gate.js` — الصفحة الرئيسية العامة: رابط "انضم كلاعب" وحده الظاهر. النقر 5 مرات متتالية (خلال ثانيتين بين كل نقرة) على العنوان الكبير يظهر رابط "الهوست" المخفي (`host.html`)
- `host.html` + `js/host-gate.js` — بوابة هوست موحدة: كلمة سر واحدة، وبعدها شاشة اختيار اللعبة الأولى أو الثانية
- `host1.html` + `js/host.js` — لوحة تحكم الهوست للعبة الأولى (خاصة بجوال مدير اللعبة)
- `display.html` + `js/display.js` — شاشة العرض (تُعرض على التلفزيون) — تخدم اللعبتين معًا وتتحول تلقائيًا بينهما فوريًا حسب `game2/activeGame`
- `admin.html` + `js/admin.js` — إدارة أسئلة اللعبة الأولى (إضافة/حذف)
- `js/sample-data.js` — سؤالان جاهزان للاستيراد التجريبي (اللعبة الأولى)
- `host2.html` + `js/host2.js` — لوحة تحكم اللعبة الثانية "أسرع واحد يضغط"، فيها أرشيف قابل للطي للأسئلة المُجابة
- `player.html` + `js/player.js` — صفحة انضمام اللاعب للعبة الثانية (تُفتح من جوال كل لاعب)
- `js/firebase-init.js` — تهيئة Firebase وشارة حالة الاتصال
- `firebase-config.js` — إعداداتك الخاصة بـ Firebase (تعبّئها بنفسك)
- `style.css` — التصميم المشترك بين كل الصفحات

الوصول للوحات التحكم (`host.html` وما بعدها) وصفحة `admin.html` غير معلن عنه من الصفحة الرئيسية — لا يظهر أي رابط مباشر لها؛ الحماية الفعلية تبقى كلمة السر (حماية واجهة بسيطة، راجع قسم "ملاحظات أمان").

## 1) تجهيز Firebase Realtime Database

1. افتح [Firebase Console](https://console.firebase.google.com) وأنشئ مشروعًا جديدًا (أو استخدم مشروعًا موجودًا).
2. من القائمة الجانبية: **Build → Realtime Database → Create Database**.
   - اختر موقع الخادم المناسب.
   - ابدأ بوضع **Test mode** (قواعد مفتوحة للقراءة/الكتابة) لتجربة سريعة. هذا يكفي لعبة داخل مكان واحد، لكن تذكر أن أي شخص يعرف رابط قاعدة البيانات يقدر يعدّل عليها. إذا تبي تشدّد الحماية لاحقًا، عدّل قواعد Realtime Database من تبويب **Rules** إلى شيء مثل:
     ```json
     {
       "rules": {
         ".read": true,
         ".write": true
       }
     }
     ```
     (هذا هو الافتراضي في Test mode، وهو كافٍ لهذا الاستخدام لأن اللاعبين لا يفتحون الموقع أصلًا.)
3. من **Project settings → General → Your apps**، أضف تطبيق ويب (Web app) واحصل على كائن `firebaseConfig`.
4. افتح ملف `firebase-config.js` في مجلد المشروع وعبّي القيم:
   ```js
   const firebaseConfig = {
     apiKey: "...",
     authDomain: "...",
     databaseURL: "...",
     projectId: "...",
     storageBucket: "...",
     messagingSenderId: "...",
     appId: "...",
   };
   ```
   أهم حقل هو `databaseURL` (يشبه `https://your-project-id-default-rtdb.firebaseio.com`) — بدونه ما راح يشتغل التزامن.

## 2) التجربة محليًا

افتح `index.html` مباشرة بالمتصفح (أو استخدم أي خادم ثابت بسيط مثل امتداد Live Server في VS Code). لا حاجة لأي تثبيت أو npm.

- افتح `admin.html` وسجّل دخول بكلمة السر الافتراضية: **`admin1234`**
  (يمكنك تغييرها بتعديل المتغير `ADMIN_PASSWORD` في أعلى ملف `js/admin.js`.)
- افتح `host.html` وسجّل دخول بكلمة السر الموحدة (نفسها بـ `HOST_GATE_PASSWORD` في `js/host-gate.js`، و`HOST_PASSWORD`/`HOST2_PASSWORD` بأعلى `js/host.js`/`js/host2.js` — الثلاثة لازم يبقوا متطابقين)، ثم اختر "اللعبة الأولى" لتصل إلى `host1.html`.
  كل الحمايات حماية واجهة بسيطة فقط (client-side)، وليست حماية أمنية حقيقية — أي شخص يفتح الكود المصدري يقدر يشوفها. `index.html` و `display.html` تبقيان بدون كلمة سر.
- من `admin.html` اضغط "استيراد أسئلة تجريبية" لإضافة سؤالين جاهزين فورًا.
- من `host1.html` اختر أحد السؤالين.
- افتح `display.html` من جهاز/تبويب آخر وشاهد التحديث الفوري عند ضغط الإجابات من الهوست.

## 3) ترتيب الأسئلة و"السؤال التالي"

زر "السؤال التالي" في لوحة الهوست يتنقل ضمن ترتيب الأسئلة كما تظهر مجمّعة حسب التصنيف في `admin.html`
(بترتيب إضافتها). لا حاجة لترتيب يدوي إضافي — فقط أضف أسئلتك بالترتيب الذي تريد لعبها به داخل كل تصنيف.

## 3.5) نظام نقاط الفريقين

اللعبة الآن بين فريقين، وبأي لحظة السؤال "عند" فريق معيّن (`game/turnTeam`). في لوحة الهوست:

- **الضغط على أي إجابة بالقائمة** = إجابة صحيحة: تُكشف الإجابة (باتجاه واحد، ما ترجع تتغطى)، نقاطها تُضاف تلقائيًا لصاحب الدور الحالي، وينتقل الدور فورًا للفريق الثاني.
- **زر "إجابة خطأ (تبديل الدور)"** = ينقل الدور للفريق الثاني بدون ما يكشف أي إجابة أو يعطي نقاط.
- **الضغط على بطاقة أي فريق** = تحكم يدوي احتياطي لتحويل الدور لذاك الفريق مباشرة.
- **أيقونة ✎ بجانب اسم الفريق** = تفتح نافذة صغيرة لإعادة تسمية الفريق (مفيدة لوضع أسماء أشخاص حقيقية).
- **زر "بدء لعبة جديدة"** = يصفّر نقاط الفريقين ويرجّع الدور للفريق الأول (بعد تأكيد، لأنه يمسح النقاط).
- أزرار "إظهار كل الإجابات"، "إعادة تعيين الجولة"، "السؤال التالي" لا تغيّر النقاط ولا الدور — النقاط والدور يبقيان محفوظين عبر كل أسئلة نفس اللعبة، وينصفّرون فقط بزر "بدء لعبة جديدة".

نفس شريط الفريقين (بدون تحكم، للعرض فقط) يظهر أعلى `display.html` ويتحدث فوريًا.

### أرشفة أسئلة اللعبة الأولى

لما سؤال "يخلص" — يعني الهوست يضغط "إظهار كل الإجابات"، أو يضغط "السؤال التالي" وكل إجاباته أصلًا مكشوفة — السؤال ينشال تلقائيًا من `questions` (القائمة النشطة اللي يختار منها الهوست ويديرها `admin.html`) وينتقل لـ `questionsArchive/{تصنيف}/{معرف}/` بنفس شكل بنك الأسئلة الأصلي (`title`, `hint`, `answers`، بدون حالة `revealed`). يظهر قسم "الأرشيف" القابل للطي أعلى قائمة الاختيار بـ `host1.html`. **تنبيه:** بما إن `admin.html` يعرض نفس عقدة `questions` مباشرة، الأسئلة المؤرشفة تختفي من قائمة "الأسئلة الموجودة" فيها أيضًا (تبقى محفوظة بـ `questionsArchive`، بس مو معروضة هناك حاليًا).

## 3.6) اللعبة الثانية: "أسرع واحد يضغط"

لعبة منفصلة تمامًا عن اللعبة الأولى، بنظام لاعبين أفراد (مو فرق) يضغطون زر "إجابة!" من جوالاتهم. تستخدم نفس `display.html` — الشاشة تتحول تلقائيًا وفوريًا بين وضعي اللعبتين (`game2/activeGame`) حسب آخر لوحة تحكم استُخدمت: اختيار أي سؤال بـ `host1.html` يرجّعها لوضع اللعبة الأولى، وبدء أي سؤال فعلي بـ `host2.html` يحوّلها لوضع اللعبة الثانية.

- ادخل `host2.html` عبر بوابة الهوست الموحدة (`host.html`) بنفس كلمة السر.
- كل لاعب يفتح `player.html` من جواله ويكتب اسمه. **يدخل بحالة "قيد الانتظار" أول** — ما ينضم فعليًا للعبة إلا بعد ما الهوست يوافق عليه صراحة من قسم "طلبات انضمام" أعلى `host2.html` (زر "موافق" لكل طلب). لين الموافقة، صفحة اللاعب تعرض "بانتظار موافقة الهوست..." وزر الإجابة مو نشط. الاسم يُحفظ محليًا (localStorage)، فما يحتاج يعيد التسجيل بعد تحديث الصفحة — بس يفضل بانتظار الموافقة لو ما وافق الهوست بعد.
- فئات الأسئلة بقائمة الاختيار بـ `host2.html` أكورديون: الضغط على فئة يفتحها ويسكر أي فئة ثانية كانت مفتوحة (فئة وحدة مفتوحة بنفس الوقت).
- الهوست يختار سؤالًا ويضغط "ابدأ الكتابة" — يبدأ يتكتب حرف بحرف بشاشة العرض.
- أول لاعب يضغط "إجابة!" توقف الكتابة له، وتظهر بشاشة العرض (وحلقة تقدّم حول زر ذاك اللاعب بصفحته) مؤقت بصري 5 ثواني بجانب اسمه (عرض بس، ما يوقف أو يأثر على أي منطق باللعبة). يحكم الهوست **صح** (نقطة + يظهر السؤال كامل، وينتقل السؤال تلقائيًا لقسم "الأرشيف" بلوحة `host2.html` عشان ما يتكرر) أو **غلط** (تكمل الكتابة تلقائيًا، وذاك اللاعب يتعطل زره لبقية هذا السؤال بس).
- الضغط محمي بـ [transaction](https://firebase.google.com/docs/database/web/read-and-write#save_data_as_transactions) على مستوى قاعدة البيانات — لو ضغط لاعبين بنفس اللحظة تقريبًا، بس أول وحد وصل فعليًا لقاعدة البيانات يفوز.
- "إعادة تعيين اللعبة" بـ `host2.html` يمسح كل اللاعبين (المعتمدين وطلبات الانتظار) ونقاطهم (بدون ما يمس الأرشيف).

هيكلة البيانات: أسئلة اللعبة الثانية النشطة تحت `questions2/{تصنيف}/{معرف}/` بحقلين فقط (`question`, `answer`) — تُضاف حاليًا يدويًا لقاعدة البيانات (لا توجد واجهة إدارة لها بعد بـ `admin.html`). الأسئلة المُجابة صح تُنقل تلقائيًا إلى `questions2Archive/{تصنيف}/{معرف}/` بنفس الشكل (تبقى محفوظة، بس منفصلة عن القائمة النشطة). حالة اللعبة الحية تحت `game2/current` (فيها أيضًا `buzzedAt` — مرجع وقت الضغط لمؤقت الـ5 ثواني). لاعبو "قيد الانتظار" تحت `game2/pendingPlayers/{اسم}/` (`requestedAt` فقط)، واللاعبون المعتمدون تحت `game2/players/{اسم}/` (`score`) — نفس العقدة المستخدمة سابقًا، ما تغيّر شكلها.

## 4) النشر (Netlify - الخيار الافتراضي)

1. افتح [app.netlify.com/drop](https://app.netlify.com/drop)
2. اسحب مجلد المشروع كامل (بما فيه `firebase-config.js` بعد تعبئته) وأفلته في الصفحة
3. Netlify يعطيك رابطًا فوريًا — افتحه من جوال الهوست وجوال/شاشة العرض

أي استضافة ثابتة أخرى تعمل بنفس الطريقة (GitHub Pages، Vercel، Firebase Hosting نفسه، إلخ) لأن الملفات خام بدون أي build step.

## 5) ملاحظات أمان

- كلمات سر `admin.html` وبوابة الهوست الموحدة `host.html` (المستخدمة قبل الدخول لـ `host1.html` أو `host2.html`) حماية واجهة فقط (client-side) لمنع الدخول العرضي، وليست حماية حقيقية ضد شخص يقرأ كود الصفحة.
- قواعد Realtime Database في وضع "Test mode" مفتوحة بالكامل. هذا مقبول للعبة تُلعب في مكان واحد ولا يفتح الموقع فيها أحد غير الهوست وشاشة العرض، لكن لا تشارك رابط `databaseURL` أو الموقع المنشور علنًا إذا ما تبي أي شخص يقدر يعدّل البيانات.
